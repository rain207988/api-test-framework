# 00 · 项目总览（api-test-framework · 文档00）

> 一句话：这是一套"企业能收"的接口自动化框架——分层解耦、数据驱动、断言分层、链路全自动、报告可视化，58 条用例 1 秒跑完。

## 1. 这个项目解决什么问题

手工回归接口的三个痛点，分别对应框架的三大能力：

| 手工测试的痛点 | 框架的解法 | 对应模块 |
|---|---|---|
| 回归 60 个接口要点 60 次 Postman，还要手动复制 token | 用例进 pytest，token 由 fixture 自动注入 | docs/08、docs/05 |
| 用例和数据耦合，改一个测试账号要改 20 个脚本 | YAML 数据驱动，数据和逻辑分离 | docs/07 |
| 响应 200 就当通过，业务失败漏测 | 三层断言：HTTP 状态码 + 业务 code + 关键字段 | docs/07(断言篇) |
| 接口失败不知道当时发了什么 | 日志 + Allure 附件自动留痕 | docs/03、docs/10 |
| 登录→下单要人工串 | 链路用例：提取变量 + 占位符自动传递 | docs/09 |
| 没人盯着回归 | CI 定时跑 + 报告推送（S14） | ../ci-cd |

## 2. 架构与六层分层

```mermaid
flowchart TD
    U[testcases 用例层<br>只表达"测什么" + 断言] --> R[api_registry 执行器<br>查注册表→调api→断言→提取]
    R --> API[api 接口业务层<br>URL 和参数结构只在这里]
    API --> C[common 公共层<br>RestClient/断言/日志/配置/token]
    DATA[data 数据层<br>YAML：51 单步 + 4 链路] --> R
    CFG[config 配置层<br>config.yaml] --> C
    C --> SUT[demo-mall 被测系统]
```

**依赖方向铁律：只能上层依赖下层（testcases → api → common），严禁反向 import。**

为什么这样分（面试主谈资，30 秒版）：

1. **用例层不含实现细节**：接口路径改了只改 api 层；测试数据变了只改 YAML；
2. **api 层不含断言**：它只负责"把接口调出来"，对不对由用例层+断言库裁决——同一接口可以被多条用例以不同期望值调用；
3. **common 层不含业务**：RestClient 不知道"商城"的存在，换一个被测系统它原样能用；
4. **common 不 import api**：401 后"怎么重新登录"属于业务，common 只定义钩子，由 conftest 注入——依赖倒置，也避免循环依赖。

## 4. 被测系统

被测对象是同目录下的 `demo-mall`（本地商城，Flask + SQLite）。
选它而不是开源大系统（RuoYi/mall）的原因：

- **零外部依赖**：不需要 MySQL/Redis/Docker，任何人 clone 后 3 条命令跑起来——README 承诺的"一键复现"才能兑现；
- **确定性**：`POST /api/test/reset` 一键重置种子数据，用例可以依赖精确值（价格 199.0、库存 100）；
- **可控的"坑"**：token 吊销接口、30 分钟过期、业务码与 HTTP 状态码分离——都是为练习框架机制量身设计的。

> 学习计划 S3 仍然会带你跑 RuoYi-Vue 练"接手陌生系统"。把本框架指向 RuoYi 只需要：改 config.yaml + 重写 api/ 层——这恰恰是分层价值的证明。

## 5. AI 时代这套东西为什么仍有含金量

AI 能帮你生成用例文本，但**把它变成可重复执行的工程**仍然是人的活：

- 判定"什么算测通过"需要业务知识（三层断言的第三层，AI 猜不出你要抽查哪个字段）；
- 数据依赖、执行顺序、环境管理（reset/种子数据）是工程决策，不是文本生成；
- CI 集成、失败留痕、报告可信度（rerun 与真失败的区分）是质量工程的核心，AI 生成的脚本没有这些照样跑不起来。

面试口径：**"AI 降低了写用例的成本，但自动化框架是质量基础设施，价值在于稳定、可重复、可审计——这正是我花力气设计分层和数据驱动的原因。"**
